the thesis

Skills can lie.

This isn't a buggy skill. The inspector's spec doesn't ask it to look at version-bound security. The failure is at the system level.

.pi/skills/project-verifier/SKILL.md

The verifier is forty lines.

SKILL.md (excerpt)
---
name: project-verifier
description: Audit a codebase against the security and supply-chain
             risks that a structural briefing misses. Trigger when the
             user asks to verify, audit, or second-opinion a project ...
---

# Process
1. Locate the dependency manifest (package.json, ...)
2. Extract pinned exact versions
3. Use web search to look up known CVE / GHSA advisories
4. Cross-reference with npm audit if available
5. Emit JSON: { verified, lens, findings[], recommendation }

It doesn't shell out to a separate process. It uses Gemini's native web grounding to look up CVEs by pinned version. Multi-CLI at the workflow altitude.

Read the description line. That's what makes Pi reach for this skill when the trigger words show up. Read the process. One thing to notice. This skill doesn't shell out to a separate process. It uses Gemini's native web grounding to look up CVEs by pinned version. Same composition move at the infrastructure altitude in Block 4.

we'll use this one

agent_end

Fires once per user prompt completion. We listen for the inspector's output shape, therefore we inject a verifier follow-up.

Pi has an extension system. TypeScript modules that subscribe to agent lifecycle events. Six events that matter for what we're building. The one we'll use is agent_end. When the agent finishes a turn, this listener checks the last assistant message and decides whether to fire a follow-up.

.pi/extensions/inspect-verify.ts

Forty lines. Two pieces.

inspect-verify.ts (the load-bearing bit)
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  // piece 1 | the ambient lesson (interactive mode)
  pi.on("agent_end", async (event) => {
    const last = lastAssistantText(event.messages);
    if (!looksLikeInspectorBriefing(last)) return;
    pi.sendUserMessage(
      "Now run project-verifier on the same target.",
      { deliverAs: "followUp" }
    );
  });

  // piece 2 | the reliable path (works in -p mode too)
  pi.registerCommand("audit", {
    description: "Inspector then verifier on a path.",
    handler: async (args) => {
      pi.sendUserMessage(coordinatedAuditPrompt(args));
    },
  });
}
Forty lines total. Two pieces. First piece: when the agent finishes a turn, this listener checks the last assistant message. If it looks like an inspector briefing, the extension injects a follow-up. Pi treats that as if you typed it, therefore the verifier fires automatically. Second piece: a slash command. Slash audit, path. Belt and suspenders.

hygiene | 3 / 3 | SYSTEM.md

Framing, not facts.

SYSTEM.md (excerpt)
You are operating inside the AI Engineering workshop repo.

- When a skill is invoked, run the skill faithfully
  and emit its declared output shape.

- Verifier skills emit JSON only. No preamble, no
  postscript.

- Honest scoping over performative thoroughness.
  A clean verifier result is a valid output.

- Cite, never fabricate, advisories. If you cannot
  verify a CVE for a pinned version, omit it.

AGENTS.md carries the conventions. SYSTEM.md carries the framing. Skills carry the reasoning. Three layers, one rule each.

This file appends to the default system prompt. Use it for framing that should shape every response in the repo. Pedagogical-honesty rules, output-shape rules, citation rules. I used to throw everything into one file, therefore my agent got confused. Now I scope by purpose.
