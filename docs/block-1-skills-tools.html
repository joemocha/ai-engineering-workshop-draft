CLI-first vs IDE-chat

5 min Lecture
Slide 1 / 3 · Two shapes

Where does the model live?

ShapeExamplesWhy it matters
IDE chatCursor, Copilot Chat, JetBrains AITight loop, lower engineering ceiling
CLI agentClaude Code, Codex CLI, Gemini CLIComposable, scriptable, higher ceiling
Slide 2 / 3 · Why CLI

CLI = composability

  • Pipes to other tools (grep, jq, gh)
  • Triggers from CI, hooks, cron, MCP servers
  • Versionable config — settings, skills, plugins on disk
  • Multi-CLI verification (run Codex + Claude on the same task)
  • This is why Sam's block lives at the CLI altitude
Slide 3 / 3 · Convergent shape

The shape is convergent

  • Prompt → plan → tool use → diff → confirm
  • Most CLIs implement some variation of this loop
  • Differences are surface, not deep
  • We'll demo with Claude Code; portability is the point
Speaker notes

Slide 1: "Two shapes of AI coding tool. IDE chat — Cursor, Copilot, JetBrains. Lives inside your editor. Tight loop, low friction, lower engineering ceiling. CLI agent — Claude Code, Codex CLI, Gemini CLI. Lives in your terminal. Composable, scriptable, higher ceiling."

Slide 2: "Why CLI matters at the engineering altitude? Composability. Pipes. Hooks. CI triggers. Multi-CLI verification — Sam will show you how to run Codex and Claude on the same task and use one to verify the other. None of that is possible inside an IDE chat. This is why every block from here on lives at the CLI altitude."

Slide 3: "The shape across CLIs is convergent. Prompt, plan, tool use, diff, confirm. Most CLIs implement some version. We'll demo with Claude Code today, but the patterns are portable."

Calibration check (from Topic 1.1 tool poll): if the room is mostly Claude Code, move on. If it's mixed, spend an extra 30s on the Codex/Gemini analogues.

Demo piece

1.3.2

Claude Code core flow

5 min Lecture
Slide 1 / 3 · The loop

Claude Code core flow

PROMPT  →  PLAN  →  TOOL USE  →  DIFF  →  CONFIRM
                                      ↑                 ↓
                                      └──── iterate ←───┘
Slide 2 / 3 · One turn

Anatomy of one turn

  • Prompt — you describe the goal
  • Plan — model proposes steps (you can edit)
  • Tool use — model edits files, runs commands, reads diagnostics
  • Diff — every write is staged as a diff
  • Confirm — you accept, reject, or redirect
Slide 3 / 3 · Plugins extend the loop

Plugins extend the loop

  • A plugin can inject skills (extra knowledge)
  • A plugin can inject slash commands (new entry points)
  • A plugin can ship its own subagents
  • The skill-creator plugin we'll use next: all three
Speaker notes

Slide 1: "Claude Code's core flow. Five nodes. Prompt, plan, tool use, diff, confirm. The loop iterates until you accept the result or quit."

Slide 2 — walk each step in ~30 sec: "Plan is the step most people skip — they hit Enter on the prompt and let the model dive in. The plan step is where you redirect early before tool-use happens. Diff is where every write lands — nothing gets written to disk without you seeing the diff first. Confirm is the human gate."

Slide 3 — bridge to Block 2: "Plugins extend this loop. They inject skills — extra knowledge the model can pull in. They inject slash commands — new entry points like /skill-creator. They can ship subagents. The skill-creator plugin we'll use in Block 2 does all three."

Demo piece — optional (~90s)

Launch claude, type a small task like "add a comment to the top of README.md explaining this is the workshop repo", walk the room through the plan → tool use → diff → confirm prompt. Don't accept — escape out at the diff. Purely to show the loop in motion.

If time is tight, skip this — Block 2.2 Beat C will show the loop in earnest.

1.3.3

★ Skill vs plugin vs agent decision framework

10 min Lecture LOAD-BEARING — DO NOT CUT

Block 2 depends on this mental model. Without it, attendees don't know why they're promoting a prompt to a skill.

Slide 1 / 4 · Four surfaces

Four ways to package AI behavior

SurfaceWhat it isWhen to reach for it
PromptPlain text, one-offSingle use, exploratory, you don't need it again
SkillSKILL.md with frontmatter + body + referencesRepeatable workflow with specific triggers; you'll want this again next week
PluginFolder bundling skills + commands + MCP serversShipping a capability to a team; needs versioning + distribution + multiple skills bundled
AgentSpecialized subagent dispatched for a taskIsolated context, parallel work, narrow capability — when you want a fresh model, not a fresh prompt
Slide 2 / 4 · Hierarchy

The packaging hierarchy

PLUGIN
  ├── SKILL  (1..N)
  │     └── prompt body + references
  ├── slash commands
  ├── MCP servers
  └── subagents (AGENTS)

Skill is the atom. Plugin is the package. Agent is the dispatcher.

Slide 3 / 4 · Decision flow

Decision questions, in order

  1. Will I use this again? No → prompt. Yes → keep going.
  2. Does it need its own context window? Yes → agent.
  3. Will I ship it to others? Yes → plugin. No → skill.
  4. Does it bundle commands + MCP + multiple skills? Yes → plugin.
Slide 4 / 4 · Five examples

Where does each example land?

ExampleSurfaceWhy
One-off PR description for a single PRPromptSingle use
Generating PR descriptions for all PRs going forwardSkillRepeatable trigger
Running 5 different code reviewers in parallel on one PRAgent(s)Isolated contexts, parallel work
Standardized incident-response toolkit for a teamPluginBundles skills + commands + RBAC
Reading a single file to answer a questionPromptSingle use, exploratory
Speaker notes

Slide 1 — walk the four surfaces: "Four ways to package AI behavior. Prompt — plain text, one-off, exploratory. Skill — a SKILL.md file with frontmatter and a body. Repeatable workflow with specific triggers. The thing you'll want next week. Plugin — a folder that bundles skills, slash commands, MCP servers, sometimes subagents. The thing you ship to a team. Agent — a specialized subagent dispatched for one task. Isolated context, parallel work, narrow capability."

Slide 2 — mental model: "Skill is the atom. Plugin is the package. Agent is the dispatcher. A plugin contains skills, but a skill doesn't need a plugin. An agent is a thing you dispatch to — not a thing you bundle. The packaging hierarchy is one of the most-asked questions on the Anthropic forums; this slide is the answer."

Slide 3 — the decision flow: "Four questions, in order. One: will I use this again? If no, prompt. If yes, keep going. Two: does it need its own context window? If yes, agent. Three: will I ship it to others? If yes, plugin. Four: does it bundle multiple skills + commands + MCP? If yes, plugin."

Slide 4 — quick test: "Five examples. Let's read them. [Walk the table.] Note that 'reading a single file' lands at prompt — you don't need a skill for one-shot reads. And 'running 5 reviewers in parallel' lands at agents, not plugins — because the parallelism + isolated context is the requirement."

Anchor: "Atom on this is Atom - Skills vs Plugins vs Agents — Decision Framework. Single most-referenced atom in this workshop. In Block 2, we'll take your v5 prompt and walk it across the boundary from prompt to skill. You'll see exactly what that promotion looks like in code."

Demo piece

None. The classification exercise in Beat 1.3.7 is where this slide gets practiced.

HO Beat B — Tour the skill-creator on disk

5 min Hands-on
Slide 1 / 3 · Where it lives

A plugin is a folder

~/.claude/plugins/marketplaces/
  claude-plugins-official/
    plugins/
      skill-creator/
Slide 2 / 3 · What's inside

The four things every plugin can ship

  • SKILL.md — the plugin's primary skill (the one Claude reads first)
  • scripts/ — Python/shell helpers the plugin invokes
  • references/ — long-form docs the skill links to (lazy-loaded)
  • agents/ — specialized subagents the plugin dispatches (e.g. grader, analyzer)
  • (skill-creator adds) eval-viewer/ — the HTML report we'll see in Block 2
Slide 3 / 3 · Why this matters

The plugin is just files

  • You can read every line of a plugin before it touches your machine
  • The grader subagent is agents/grader.md
  • The eval-viewer is a Python script you can run yourself
  • No magic. Just structured files.
Speaker notes

Slide 1: "A plugin is a folder. Yours is at ~/.claude/plugins/marketplaces/claude-plugins-official/plugins/skill-creator/. Open it in your editor or just ls it. Look at it."

Slide 2 — walk the folder shape: "Inside, you'll see four kinds of things every plugin can ship. SKILL.md is the primary skill — what Claude reads first. The scripts directory holds helpers — the description optimizer we'll use in Block 2.3 lives there. References are long-form docs lazy-loaded when the skill needs them. Agents are specialized subagents — skill-creator ships a grader and an analyzer. And skill-creator adds an eval-viewer — the HTML report we'll meet in Block 2 Beat E."

Slide 3 — the anchor: "The plugin is just files. No magic. You can read every line before it touches your machine. That's why we're spending five minutes on disk-tour — when something doesn't work in Block 2, you can cat the agent prompts and see exactly what's happening."

Demo piece — attendees + instructor mirror

1.3.7

HO Beat C — "Which is this?" classification

10 min Hands-on · discussion
Slide 1 / 6 · Setup

Which surface is this?

  • 5 scenarios on screen, one at a time
  • Vote: prompt / skill / plugin / agent
  • 1 min per scenario, then group discussion
  • No wrong answers — only better justifications
Slide 2 / 6 · Scenario 1

Scenario 1

"I want to generate a PR description for the PR I just opened. It's a one-line bugfix."

Vote: prompt / skill / plugin / agent

Expected answer: prompt — single use, no future reuse intended

Slide 3 / 6 · Scenario 2

Scenario 2

"Every time anyone on my team opens a PR, they should get an auto-generated description following our team's format. I want this to be a hooked-in workflow."

Vote: prompt / skill / plugin / agent

Expected answer: skill (or plugin if it bundles a hook + slash commands)

Slide 4 / 6 · Scenario 3

Scenario 3

"I want to run a security reviewer, a performance reviewer, and a style reviewer on the same PR simultaneously, each in their own fresh context, then merge their findings."

Vote: prompt / skill / plugin / agent

Expected answer: agent(s) — parallel isolated contexts, narrow capability

Slide 5 / 6 · Scenario 4

Scenario 4

"My company has 15 internal AI-coding workflows: incident response, RFC scaffolding, code-review checklists, deploy verification, oncall handoffs. I want one install that gives every engineer all 15."

Vote: prompt / skill / plugin / agent

Expected answer: plugin — bundles skills + slash commands + (probably) MCP servers, ships to a team

Slide 6 / 6 · Scenario 5

Scenario 5

"I want to ask the model what's in this single config file so I understand the timeout values."

Vote: prompt / skill / plugin / agent

Expected answer: prompt — single-shot read, no reuse planned

Speaker notes

Slide 1 — set the exercise: "Five scenarios. For each one, vote: prompt, skill, plugin, or agent? Show of hands or shout it out. One minute per scenario, then we discuss. No wrong answers — only better justifications."

For each scenario:

  1. Read the scenario aloud
  2. Pause ~20s
  3. "Vote — prompt? Skill? Plugin? Agent?" (count hands)
  4. Pick someone who voted differently — "why did you say [X]?"
  5. Affirm or redirect based on the expected answer
  6. Move to next slide

Scenario 1 (prompt): "Why prompt? Single use. You're not going to need this exact PR description again. Don't pay the cost of a skill."

Scenario 2 (skill, possibly plugin): "Skill is the canonical answer — repeatable, specific trigger ('every PR open'). Plugin if it also ships a hook and a slash command alongside the skill. Both are defensible."

Scenario 3 (agents): "Three reviewers, three isolated contexts, parallel. That's the agent-dispatch pattern. A single skill couldn't keep the three contexts isolated."

Scenario 4 (plugin): "Fifteen workflows, one install, distributed to a team. That's the plugin definition. Skill is too small; agent is the wrong shape."

Scenario 5 (prompt): "Single config read. No skill needed. Don't over-engineer one-shot reads."

Close: "This is the muscle you're going to use every time you decide whether to invest in a skill. If the answer is 'I'll use this once,' it's a prompt. The moment you say 'I want this again,' you're at skill. The moment you say 'I want this for the whole team,' you're at plugin."

Demo piece

None — pure discussion. Use hand-raises or call-outs; no terminals open.
